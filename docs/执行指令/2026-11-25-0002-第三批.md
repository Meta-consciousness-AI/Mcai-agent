## 我们的指令是

请 `0002` 改 `deploy/push-gitee.ps1`，共四处。前三处是这次失败的直接教训，第四处是把「推成功」变成可核的事实。

### 一、令牌来源：先凭据库，后剪贴板，并校验形状

现状：脚本只从剪贴板取令牌，唯一的校验是 `$token.Length -lt 16`。2026-11-25 实测：剪贴板里放着我给的命令文本（远超 16 字符），被当成令牌发了出去，返回一句通用失败文案，看不出真因。

要的行为：

1. 优先从凭据库读：`E:\th\元意识\元意识运营\Mcai-Agent\mcai-knowledge\Gitee令牌.txt`（这是 2026-11-25 定的唯一凭据位置，见 `docs/工作原则.md`「凭据存放处」）；
2. 读不到再退回剪贴板；
3. 两处都拿不到就报错退出，提示「令牌请放进凭据库或复制到剪贴板」；
4. **校验形状**：Gitee 私人令牌为 32 位十六进制，用 `^[0-9a-fA-F]{32}$` 判断；不符就停下，并明确提示「这不像令牌，可能是剪贴板里放的是别的内容」；
5. 无论走哪条路，都打印 `len=<长度> shape=<OK|不对>`，长度与形状不对立即退出，不要带着可疑令牌去连。

### 二、失败时打印 git 的原话

现状：第 41 行只抛出自己写的「推送失败（令牌权限、仓库地址有误，或非快进被拒…）」，把 git 的真实输出丢了。这正是「不要把子进程的 stderr 丢进 `$null`」的同一条教训（`docs/工作原则.md`「脚本与系统文件」）。

要的行为：把 `git push` 的 stdout 与 stderr 捕获下来，失败时先打印「git 原话：」＋原始输出的前若干行（建议 8～15 行），再抛出通用提示。

### 三、令牌不许出现在任何输出里

因为会把 git 原话打出来，而 git 的报错可能带着含令牌的 URL，所以打印前必须先做替换：把令牌字符串（以及 URL 里的 `oauth2:<token>` 段）替换成 `***` 再输出。**任何一段输出里都不得出现令牌明文。**

### 四、推送后复核远端 sha

现状：打印「✅ 已推送到 Gitee」就算完，没有核对远端到底到了哪个提交。2026-11-25 之前几次「推成功」后来发现都走了 DNS、与固定无关，就是因为没有复核。

要的行为：推送后跑一次 `git ls-remote <remote> refs/heads/master`，与本机 `HEAD` 比对；一致才打印成功并给出 sha，不一致则报「推送后复核不一致：远端 X，本机 Y」并退出非 0。

### 五、去掉不可靠的交互式输入

`Read-Host -AsSecureString` 在这个 console 里粘贴不完整（2026-11-25 两次都只拿到不足 16 个字符），不作为入口。剪贴板也拿不到时，直接报错让用户把令牌写进凭据库，不要给一个坏用的输入框。
