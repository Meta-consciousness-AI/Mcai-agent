# 研究：核验器、标准与护城河

> 时间：2026-11-16
> 背景：从「知识库」转向「核验器」，需要回答：这是不是一时的想法？标准能不能立？护城河在哪？

## 二、为什么现在可以认真谈标准

1. 需求侧有证据：编辑、作者、媒体都在人工核对引文（见 `研究-需求-引文核对.md`）；
2. 供给侧有空档：黑马校对偏格式与书目，自动改写式工具会制造错误；
3. 我们已有资产：验证器、评测基准、出处规范、工具链；
4. 信任研究指明边界：Web3 只能证明「没被改」，证明不了「对不对」，而「对不对」正是标准要定义的。

## 三、什么可以成为标准

标准不是「我们的产品」，是**别人愿意照着做的一套约定**。

候选对象，按可行性排：

| 对象 | 内容 | 可行性 |
|---|---|---|
| 指标定义 | 引用忠实度、逐字命中率、区间一致率、拒答准确率 | 高：已有基准 |
| 报告格式 | 核验报告字段（来源、区间、差异、结论） | 高：已有输出 |
| 流程规范 | 分层定义、单字术语、版本并存、缺失即拒答 | 中：已有 V1.1–V1.3 |
| 评测基准 | 公开题库 + 评分脚本 + 排行榜 | 中：已有四层 78 题 |
| 认证 / 凭证 | 签名核验报告、知识包质量凭证 | 中：待做 |
| 互认协议 | 不同知识包之间的对照与翻译 | 低：需多方参与 |

## 四、护城河在哪

### 能积累的

1. **基准与题库**：越多人用，越有可比性；
2. **规则库与失败案例库**：什么文本做不成、哪里会翻车，只有做过的人知道；
3. **被引用**：论文、标准草案、行业文章引用我们的指标；
4. **认证记录**：谁通过了、谁没通过，形成公开账本；
5. **工具链生态**：别人用我们的工具产出知识包；
6. **品牌信用**：不夸大、可回查，长期积累。

### 不能积累的

- 代码：会被复制；
- 单个工具：会被替代；
- 提示词：会过时；
- 一次性的数据：会被追上。

### 关键判断

标准的护城河**不靠用户量，靠被采用**。

一个只有 100 个用户、但被 3 家出版社写进流程的标准，比 10 万用户的自用工具更有护城河。

## 五、路径（开源规范 + 参考实现 + 公开基准 + 试点）

### S1 规范草案（1–2 周）

- 写一份 RFC 风格的《引用核验规范 v0.1》；
- 定义指标、报告字段、判定规则；
- 先给 3–5 个人看，不公开宣传。

### S2 参考实现（已有，需整理）

- 把 `mcai-verify` 整理成独立、可安装的工具；
- 附示例数据与报告样例。

### S3 公开基准（2–3 周）

- 发布 78 题基准与评分脚本；
- 给出基线分数，允许他人提交结果。

### S4 试点（1–2 个月）

- 找 1–2 家出版社或期刊，用规范跑一遍真实书稿；
- 拿到「用了之后差多少」的数据。

### S5 凭证（试点后）

- 签名核验报告；
- 与 C2PA / VC 格式对齐。

### S6 联盟（长期）

- 有 3 家以上机构采用后，再谈标准组织或联盟；
- 在此之前，自封标准没有意义。

## 六、前期要做的大量工作

1. 术语统一：核验、校验、核对、溯源，先定义清楚；
2. 指标可复现：同一份报告，两个人跑出同样结果；
3. 反例库：收集真实错误案例（错字、漏字、张冠李戴、版本混淆）；
4. 与现有标准对齐：C2PA、VC、GB/T 7714、DOI；
5. 法务与署名：规范以谁的名义发布；
6. 社区：至少有一个公开讨论的地方。

## 七、风险

1. **自封标准**：没人用，反而显得自大；
2. **被大厂覆盖**：WPS、知网若开放核验接口，我们空间被压缩；
3. **Web3 误读**：一提链就被当成炒币；
4. **标准太窄**：只适用于古籍，无法扩展；
5. **标准太宽**：什么都想管，没人照做。

## 八、与现有计划的关系

- P1 验证器、P2 基准是 S1–S3 的基础；
- 不新增开发，先把「规范 + 基准 + 试点」做出来；
- Web3 只在 S5 之后作为可选层。

## 九、建议的第一步

**写《引用核验规范 v0.1》**，不超过 10 页，包含：

- 适用范围；
- 四个指标；
- 报告字段；
- 判定规则；
- 两个完整示例。

写完先给 3 个人看，不发布。
