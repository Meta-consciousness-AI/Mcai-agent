# 研判：核验器方向的赛道、分支与可行性

> 时间：2026-11-16
> 方法：全网检索论文、行业产品、标准与市场，不预设结论。
> 结论先说：方向对，但要选对分支——**做「引文忠实度的度量标准与凭证」，不做「又一个查重/查参考文献工具」**。

## 一、赛道地图（四段）

### 段 1：参考文献元数据核验

做法：把一条参考文献的作者、期刊、年份、DOI 与 Crossref/Semantic Scholar/OpenAlex 比对。

代表：

- [RefChecker](https://pypi.org/project/academic-refchecker/)：开源，支持 PDF/arXiv，查 DOI、作者、标题是否匹配；
- [Edifix](https://www.edifix.com/)（Inera/Atypon，Wiley 系）：出版社在用的参考文献校对，含撤稿检测、Cabells 掠夺性期刊库；
- [CoChat](https://edtechchronicle.com/marcel-folaron-ceo-founder-cochat-answers-five-questions-for-founders/)：AI 研究工具，宣称对 CrossRef/Semantic Scholar 校验引用与引文。

判断：**成熟、拥挤、护城河低**。数据源是公开的，谁都能做。

### 段 2：引文忠实度核验（引文 vs 原文）

做法：不是查「这条文献存不存在」，而是查「你引的这句话，在原文里是不是逐字存在、位置对不对」。

代表（学术侧）：

- [ALCE](https://arxiv.org/abs/2305.14627)：自动评测引文质量（fluency / correctness / citation quality）；
- [CiteEval](https://arxiv.org/abs/2501.15033)、AtomCite、DocCite：引文支持度检测与基准；
- [《Evaluating and Guarding Citation Faithfulness in Agentic Scientific Synthesis》](https://browse-export.arxiv.org/pdf/2607.20527)：提出「没有具名验证器与协议，跨论文比较无效」，并用 gold-anchored 协议与 conformal guard 给出可核查的保证。

判断：**学术上正在成型，产品上几乎没有**。这是空档。

### 段 3：出版业诚信筛查

做法：论文工厂、图像重复、数据造假、引用堆叠的整体筛查。

代表：

- [STM Integrity Hub](https://www.csescienceeditor.org/article/the-stm-integrity-hub/)：40 家出版社、每月 12.5 万篇、每月拦截约 1000 篇疑似论文工厂投稿；
- [NISO CREC](https://www.zenodo.org/records/13175116)：撤稿/更正传播的推荐实践；
- 各类图像查重、StatReviewer 等。

判断：**由行业联盟与巨头主导，门槛极高**，不是我们能进的段。

### 段 4：AI 生成内容的引用核验

做法：给 RAG/Agent 的输出做引用校验，或给写作工具做「引用前验证」。

代表：

- 学术基准（ALCE/CiteEval）；
- 产品（CoChat、各类 AI 写作插件）；
- 标准侧：C2PA 做内容来源，不做「对不对」。

判断：**早期，需求增长快，标准未定**，与我们的能力最匹配。

## 二、分支与我们可能成为什么

| 分支 | 做什么 | 竞争 | 我们成为 |
|---|---|---|---|
| A 参考文献核验工具 | 查 DOI/作者/期刊 | RefChecker、Edifix、CoChat | 又一个免费工具，无护城河 |
| B 出版社引文核对服务 | 帮出版社核书稿引文 | Edifix、黑马校对 | 一家服务商，项目制 |
| C **引文忠实度标准 + 基准** | 定义指标、报告、评分，开放基准 | 学界有论文，无产品标准 | **度量标准的制定者** |
| D Agent 引用核验基础设施 | 给 Agent 提供核验 API/凭证 | 早期，无主导者 | **Agent 的引用质检层** |
| E 内容来源凭证 | C2PA 式来源声明 | C2PA 联盟、大厂 | 跟随者，不做 |

**建议：C + D。**

- C 是「标准与基准」，慢但护城河深；
- D 是「Agent 基础设施」，快但需要生态；
- 两者共用同一套指标与实现，C 为 D 提供公信力，D 为 C 提供使用量。

## 三、如果走 C+D，我们成为什么

> **引文忠实度的「计量局 + 质检章」。**

- 不定内容对错，只定「引用是否忠实」；
- 提供公开基准，谁都可以来测；
- 出具可验证的核验报告（签名、可追溯）；
- 出版社用它做验收，Agent 平台用它做质检。

不成为：内容供应商、查重公司、论文工厂检测商。

## 四、我们的条件与短板

### 已有条件

1. 可运行的核验器（逐字、区间、版本、拒答）；
2. 四层评测基准（78 题）；
3. 出处规范 V1.1–V1.3；
4. 工具链（validate/package/all）；
5. 中英双语文档与发布能力；
6. 长期主义的耐心。

### 短板

| 短板 | 影响 | 补法 |
|---|---|---|
| 没有 PDF/OCR 管线 | 无法处理扫描书稿 | 用现成库或外包 |
| 没有出版社关系 | 拿不到试点 | 先找 1 家小社/期刊 |
| 没有学术背书 | 标准难被信 | 投一篇方法论文/预印本 |
| 没有销售 | 服务难落地 | 先做 1 个付费试点 |
| 语料覆盖窄 | 只擅长中文古籍与自家库 | 用用户自带原文规避 |
| 团队小 | 无法同时做标准与产品 | 只做 C，D 等生态 |

## 五、资源需求（12 个月视角）

| 资源 | 用途 | 估算 |
|---|---|---|
| 规范写作 | 指标、报告、判定 | 1–2 人月 |
| 参考实现 | 开源工具 + 示例 | 1 人月 |
| 公开基准 | 题库、评分、榜单 | 1 人月 |
| 试点 | 1–2 家出版社 | 2–3 人月 |
| 学术背书 | 预印本/论文 | 1 人月 |
| 法务与署名 | 规范发布主体 | 少量 |

总计约 6–8 人月，可分散在 12 个月内完成。

## 六、借鉴「中华经典」的教训

上次停下的原因：先建东西，再找使用者；条件一变（账号/成本），就停。

这次反过来：

1. **先拿试点意向**：在写规范前，先找 1 家愿意试的出版社或期刊；
2. **设里程碑与止损点**：
   - 第 4 周：规范 v0.1 + 1 个试点意向；
   - 第 12 周：试点跑完一份真实书稿，有差异报告；
   - 第 24 周：公开基准上线，有外部提交；
   - 任一节点不达标，暂停，不硬撑。
3. **不建平台**：只做规范、工具、基准、报告，不做 SaaS。

## 七、风险

1. **标准自封**：没人采用就是自娱；
2. **被巨头覆盖**：WPS/知网若开放核验 API，空间被压；
3. **学术竞争**：ALCE/CiteEval 等已占「基准」名分；
4. **付费方保守**：出版社流程慢，试点周期长；
5. **PDF 质量**：扫描件提取差，核验率低。

## 八、结论

- 方向成立，但**不能做 A**（红海）；
- **C 是唯一能形成长期护城河的分支**，D 是其自然延伸；
- 成败不在技术，在**能否拿到第一个真实试点**；
- 先做规范与基准，不做平台。

## 九、下一步建议

1. 写《引用核验规范 v0.1》（1–2 周）；
2. 同时找 3 家潜在试点（出版社/期刊/Agent 团队）；
3. 有 1 家点头，再投入参考实现与基准公开；
4. 没有试点，就停在规范阶段，不扩大。
