# 工作法：平台接入可行性调查

> 起因：2026-11-20 做豆包/扣子接入，技术做通了，才发现平台通道不开放。
> 结论：**先调查平台，再写代码；技术可行不等于平台允许，更不等于用户可达。**

## 一、五问清单

任何平台，动手前先回答：

1. **官方入口是否存在？**
   - 是「技能商店」「MCP 广场」「插件市场」，还是只能私有部署？
   - 最近一次官方公告是什么时候？政策有没有变？

2. **账号与资质是否满足？**
   - 个人账号能否提交？
   - 是否要求企业认证、成立年限、客户数量、邀请码？

3. **提交格式与审核**
   - 要 MCP URL、OpenAPI、插件包，还是技能 zip？
   - 审核周期多久？会不会要求备案/软著/隐私政策？

4. **上架后用户怎么发现？**
   - 平台内搜索、分类目录、首页推荐，还是只有链接？
   - 是「所有人可见」还是「登录用户可见」？

5. **维护与下线风险**
   - 平台是否曾下线该渠道？
   - 版本更新要不要重新审核？
   - 平台抽成、限流、收费规则是什么？

## 二、三种「可行」要分开

| 层次 | 问题 | 例子 |
|---|---|---|
| 技术可行 | 接口能不能通？ | 远程 MCP 能握手、能调工具 |
| 平台允许 | 让不让上架？ | 豆包技能商店不开放个人上架 |
| 用户可达 | 上架后有没有人能看到？ | 扣子→豆包渠道 2026-07-01 已下线 |

三者都成立，才值得投入平台适配。

## 三、扣子/豆包案例

**做了什么**

- 远程技能包；
- 豆包本地技能改为远程；
- 扣子插件、智能体、发布到扣子商店。

**结果**

- 技术全部跑通；
- 豆包技能商店不开放个人自定义技能；
- 扣子→豆包发布渠道已下线；
- 最终只触达扣子用户，不是豆包用户。

**可复用**

- 公网 API、MCP、公开问答页；
- 通用远程技能包；
- 扣子智能体（扣子用户可用）。

**教训**

- 把「技术能接」当成「平台能上」；
- 没先查平台公告与入口；
- 先做了豆包专用适配，后知道通道不存在。

## 四、执行规则

1. 新平台先填五问清单，**只查不做**；
2. 五问里任何一项为「否」，先不写适配代码；
3. 至少确认「官方入口 + 账号资质 + 上架后可见」三项；
4. 调查结论写入 `docs/渠道台账.md`，再决定是否投入；
5. 平台政策标注日期，季度复查。
