# DSH 会话与上下文机制

> 研究日期：2026-11-22
> 来源：当前安装包 `app.asar` 内的 `dsh-compaction-basic`、`dsh-command-compact`、`dsh-agent-loop`、`dsh-api-session-controller` 文档。

## 一、事实

### 1. 会话没有轮次/步数硬上限

- Session 是持久化事件日志；
- 每个 turn 由若干 step 组成；
- `dsh-agent-loop` 明确写明：**没有内置轮次预算**；失控轮次要靠扩展点取消。

所以「多少轮必须换会话」不是 DSH 的硬规则。

### 2. 真正的限制是上下文窗口

- 自动压缩（compaction）在 token 压力接近模型上下文上限时触发；
- 默认阈值：

```
floor(min(W × 0.8, W − O − 65536))
```

- W = 上下文窗口；O = 输出预留；默认余量 65,536 tokens；
- 近期历史逐字保留预算约为 `W − O` 的 16%；
- 达到阈值后，把最旧的一段历史替换为摘要，近期消息保留；
- 提供方报上下文溢出后，会压缩并重试一次。

### 3. 可以手动压缩

- `/compact` 命令：即使没到压力阈值，也可以立即压缩；
- 执行时会报告压缩了多少历史项、估算节省多少 token；
- agent 正在轮次中或压缩已在运行时，命令暂不可用。

### 4. 压缩有代价

- 压缩需要一次额外的模型请求；
- 旧历史被摘要替换，细节可能丢失；
- 摘要保留在 `compaction/summary` 事件里，但后续请求看到的是摘要；
- 系统提示词、工具、单个超大工具调用，压缩不一定能缩减。

### 5. 会话可以归档

- 归档后，迟到唤醒会被拒绝，不再发起新步骤；
- 需要时取消归档即可解除；
- 归档不是删除，归档会话仍可恢复。

## 二、预判

1. **轮次和步数只能看工作量，不能当硬限制**；
2. 真正该看的是：上下文百分比、任务是否收口、是否频繁 transport failed；
3. 长会话即使没溢出，延迟、重试、缓存失配也会变差；
4. 压缩后仍能工作，但细节会丢，所以关键决定必须写进文件；
5. 主会话 2045 轮 / 6362 步 / 45% 上下文，已经属于“超大”，不应再承担执行。

## 三、量化建议（待确认）

### 会话数量

| 状态 | 上限 |
|---|---:|
| 一般工作 | 3 个 |
| 工作量大 | 5 个 |
| 工作量超大 | 9 个（硬上限） |

### 单会话工作量

| 级别 | 用户轮次 | 工具步数 | 上下文 | 处理 |
|---|---:|---:|---:|---|
| 轻 | < 30 | < 150 | < 10% | 可并入现有会话 |
| 标准 | 30–100 | 150–500 | 10–30% | 一个专项会话 |
| 重 | 100–300 | 500–1500 | 30–50% | 50% 前主动 `/compact`，尽快收口 |
| 超大 | > 300 | > 1500 | > 50% | 只做决策，不再执行 |

### 主动阈值

- **50%**：重任务开始收尾，准备 `/compact`；
- **60%**：不再接新执行，更新 HANDOFF；
- **70%**：必须压缩或换会话；
- **80%**：自动压缩会介入，已偏晚。

### 专项会话最低工作量

避免 ops 这种 7 轮 / 80 步就单独开一个会话：

- 至少 30 分钟、30 个用户轮次或 100 个工具步；
- 或有一个明确、独立的交付物；
- 否则并入现有会话。

## 四、对当前的判断

- 主会话：2045 轮 / 6362 步 / 45%，**超大，只做决策**；
- ops：7 轮 / 80 步，**轻量**，以后这类任务并入 platform 或 ops 批量做；
- platform：3 轮 / 81 步，**轻量**，可继续承担平台类小任务；
- 内容审校如果启动，预计标准到重，应单开 `mcai-knowledge-content`。
