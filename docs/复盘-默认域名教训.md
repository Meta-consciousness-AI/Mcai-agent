# 复盘：默认域名访问上限的教训

> 时间：2026-11-11
> 性质：工作方法复盘，不是事故追责
> 结论：不是执行出错，是**动手前的调查不够**。

## 一、事情经过

| 时间 | 事件 |
|---|---|
| 2026-10-29 | 站点上线，使用 CloudBase 默认域名 `*.tcloudbaseapp.com` |
| 2026-11-10 13:37 | 文章在知乎、公众号、掘金、微博发布，站点作为主入口 |
| 2026-11-10 23:00 | 读者反馈「访问达到上限」 |
| 2026-11-10 23:58 | 查日志：24 小时内 `/index.html` 仅 32 次请求 |
| 2026-11-11 | 确认是默认域名风控，不是流量大 |

## 二、预期与实际

| 项 | 我们以为 | 实际 |
|---|---|---|
| 默认域名 | 可以正常对外使用 | 浏览器访问出中间页，非导航请求加 `attachment` |
| 访问额度 | 足够日常使用 | 极低，几十次请求即触发「访问达到上限」 |
| 手机打开 | 正常渲染 | 变成下载 `download.html` |
| 平台外链 | 知乎、微信可点 | 被判低信任，出现风险页或拦截 |

## 三、根因

1. **没有查官方文档**：CloudBase 明确写了默认域名仅供测试、有中间页与风控，移除只能靠自定义域名（需 ICP 备案）；
2. **把「能跑通」当成「能对外」**：本地与桌面测试正常，就默认对外可用；
3. **没有做「失败边界」调查**：没问「这个方案在什么条件下会失效、失效时什么样」；
4. **把入口假设成了稳定设施**：实际上它是最脆弱的一层。

## 四、代价

- 时间：搭站、上传、改文章、四个平台返工；
- 信任：读者点开看到下载页或风险页；
- 预期：本希望站点成为主入口，结果只能降级为「开发预览」。

## 五、五条教训

1. **对外可见的东西，先查平台限制，再动手**；
2. **「能访问」不等于「能对外」**：要分别测桌面、手机、微信、知乎、无痕；
3. **所有免费/默认资源，都要问额度与失效方式**；
4. **入口要可替换**：不要把主入口绑在单一平台的默认资源上；
5. **先做一次「最坏情况演练」**：如果它明天挂了，读者还能不能找到我们？

## 六、新增前置检查（写作「对外搭建前调查」）

任何对外可见的搭建（站点、接口、表单、页面、机器人）开始前，先写一页调查：

- [ ] 平台官方文档里，这项能力的**使用限制**是什么？
- [ ] 免费/默认资源的**额度**是多少？超了会怎样？
- [ ] **失效时的表现**是什么（报错、中间页、下载、封禁）？
- [ ] 目标分发平台（知乎、微信、微博、掘金）**是否信任这个域名**？
- [ ] 有没有**替代方案**？切换成本多少？
- [ ] 如果明天停服，**恢复路径**是什么？

六项里有一项答不上来，就先不做，或先做小规模验证。

## 七、一句话

**不是不能犯错，是不能在同一个地方，用「没查」的方式犯错。**
