# 复盘：0.4.0 发布

> 时间：2026-11-19
> 结果：已上线。public / gitee 两个服务均为 0.4.0，内容已核验。
> 代价：多花了约 1.5 小时，经历了 3 次失败部署。

## 一、出了什么问题

| # | 问题 | 表现 |
|---|---|---|
| 1 | Gitee 分支分叉 | `main` 停在旧提交，`master` 才是最新；服务默认部署 `main`，所以一直是 0.3.9 |
| 2 | Dockerfile 复制了被 gitignore 的文件 | 构建报 `config/corpus.json not found`、`data/kb.json not found` |
| 3 | 部署方式没记录 | 「更新服务」打开是空的 Git 部署表单，不知道之前用的仓库和分支 |
| 4 | 核验只看版本号 | 没同时看内容和 `built_at`，多绕了几轮 |
| 5 | 操作没有分解 | 一次给一整页步骤，中间错了也不知道错在哪一步 |

## 二、根因

1. **分支没有收敛**：同一仓库两个分支，长期不合并，部署方默认取 `main`；
2. **构建上下文没有检查**：`.gitignore` 排除了 `data/kb.json`，Dockerfile 却要复制它；
3. **发布流程没有沉淀**：部署入口、仓库、分支、端口这些信息只存在记忆里；
4. **验证标准不完整**：版本对了不等于内容对了，内容对了不等于构建来源对了。

## 三、已经做的修复

- 部署分支改为 `master`；
- Dockerfile 改回使用包内已跟踪的 `mcai/data/default/data/kb.json`；
- `.dockerignore` 与 Dockerfile 对齐；
- 新增 `tools/preflight_release.py`：检查版本一致性、Docker COPY 源是否存在且未被忽略、包内知识库是否被跟踪；
- 新增发布检查清单。

## 四、分支收敛（已解决）

Gitee 仓库原本同时有 `main`（旧）和 `master`（新），部署默认取 `main`，导致一直发布旧代码。

2026-11-19 已处理：

- 默认分支改为 `master`；
- 删除 `main`；
- 现在 Gitee 只剩 `master`，不会再选错。

## 五、可复用的经验

1. **外部控制台操作，一步一确认**：给一步、做一步、看结果、再下一步；
2. **部署前三查**：分支、构建上下文、包内数据版本；
3. **部署后三验**：health 版本、`built_at`、一条内容抽检；
4. **每次部署记录**：仓库、分支、提交号、部署 ID；
5. **不让分支分叉**：main / master 只保留一个有效分支，或每次推送同时更新两个。

## 六、一句话

不是技术难题，是**流程没有闭环**：分支、构建、部署、核验，每一步都少了一个确认。
